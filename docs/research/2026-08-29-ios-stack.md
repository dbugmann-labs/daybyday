# Which stack to build DayByDay in

**Status: findings, not a decision.** Recorded 2026-08-29 so the ADR that follows is written
from verified facts rather than from memory. The decision itself belongs in `docs/adr/1001-*`.

## The question

DayByDay is an iPhone app. This repository's machinery is TypeScript and Node. What language
and stack should the product be written in, and what does that cost?

## Constraints that decided it

- **iPhone only.** One platform, for the repo owner's own use. A second platform may never exist.
- **Solo, 4–8 hours a week.** Time is the binding constraint; money and performance are not.
- **Small and offline.** Recurring commitments, a date-driven due-or-not rule, a list screen
  with tap-to-tick, an edit screen. No networking, no backend, no account.
- **HealthKit matters later.** Weight and dietary protein are native HealthKit types.
- **Acceptance tests attach to one seam** — an exported entry point a test drives directly,
  without spawning a process or capturing global streams.

## The options, and how they fared

**Swift + SwiftUI — chosen direction.** The rule engine ("is this commitment due on this
date") is pure logic and can live in a Swift Package with no UI, tested with Swift Testing and
run from the terminal by `swift test`. That is the cleanest seam of any option here, and it is
the shape this repository's pipeline is built around. SwiftData is adequate for a data set this
small; GRDB is the escape hatch if it ever is not. Cost: Swift is a new language for the owner,
realistically 20–40 hours before fluency — four to seven weeks of the weekly budget.

**Expo / React Native — the serious alternative.** Reuses the owner's TypeScript and much of
this repo's tooling, and is the fastest route to a working screen. The trade is a permanent
layer of indirection and a third-party dependency for HealthKit.

**Kotlin Multiplatform — rejected, but not for being immature.** Compose Multiplatform for iOS
has been Stable since 1.8.0 (May 2025) and runs in production at Netflix and Cash App. It is
rejected because its entire value is sharing logic across platforms and there is one platform;
the shared logic here is a date predicate of a few hundred lines. HealthKit would still be a
Swift bridge.

**Home-screen PWA — rejected on a stated requirement.** The usual objections are stale: home
screen web apps are exempt from Safari's seven-day script-storage cap and have supported push
since iOS 16.4. It fails because its data lives in browser storage that Safari can evict, and
the durable record is the entire point of this product — see `docs/parking-lot.md`.

app opened several times a day.

## What this repository would have to change

Five of the six merge-time checks read only git history, the GitHub API and markdown under
`openspec/`. They are language-agnostic and survive untouched. **The single coupling is
`scripts/check-scenario-coverage.ts`**, which enumerates acceptance-test titles by shelling out
to `pnpm exec vitest list --json`. That one call has to learn to list Swift test names. The
second is CI step 7 (`pnpm run verify`), which needs a parallel job on a macOS runner.

## What this does not settle

SwiftData versus GRDB. Whether the Node tooling stays in this repository long-term. How
`check-scenario-coverage.ts` should enumerate Swift tests. None of those block the ADR.
