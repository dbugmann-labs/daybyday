From parking lot
to main

DayByDay is an iPhone app for the commitments you owe yourself and the rhythm each one runs on. It is built with Atlas, the development system this repository was started from — signed off on 24 August 2026 and inherited here rather than invented. The product half is what is new: an idea is not agreed until it has passed G4 as a requirement in a change folder, and everything before that is a line in the parking lot, however confident anyone sounded when they said it.

Before Stage 0: where the product comes from

The pipeline receives a body of work; it does not discover one. Product definition sits upstream of Stage 0 and is deliberately not a numbered stage, because it is a conversation rather than a pipeline with gates. It has one rule and one artifact.

The line, end to end

Nine stages, five gates — numbered 0 to 9 with no Stage 3, where the grill used to be. A gate is a place where work stops until a named condition holds; colour says who clears it — a human, or the machine.

Who drives

The session talking to you is the conductor, and /atlas is how it runs. It reads status, spawns the agent whose turn it is, and stops at every gate that needs you. It holds no work context of its own: no delta, no test, no src/.

Every gate stop takes one shape

Five parts, in this order, and nothing else — no praise, no recap of the pipeline, no options you did not ask for. A gate whose presentation is improvised each time is a gate that quietly becomes a rubber stamp, and G4 is the one the whole requirement set rests on.

Illustrative: Story #8 has no change folder yet. The form is specified in .claude/commands/atlas.md and docs/process.md §4.

The recommendation is part of the form, not a courtesy. The gate arrives after an agent has spent an hour on the thing being judged, and without a stated lean the cheapest reply is always yes — which is a rubber stamp with extra steps. It is also the one part that can be wrong out loud: the conductor spawned the spec-author whose delta is on the table, so recommending changes: against its own subagent is what makes the rest worth reading. It is an argument to reject, never a reason to answer without opening the PR.

Three levels, three anchors

The repo owns content; GitHub owns state and order. Nothing is written down twice — an issue body holds a sentence of intent, a link, and gate checkboxes, never requirements.

Read the bold entries down the driver column and you have the whole obligation: four stops — G1, G2, G4, G7 — plus answering, inside Stage 4, any round the grill raises because it could not settle it on its own. Stages 5, 6, 8 and 9 never wait for you.

There is no Stage 3. The grill was one until 30 August 2026, when it was folded into Stage 4 — the first cut on docs/process.md §12's list, taken because at one concurrent Story it never justified a session of its own. Its obligations moved with it and none of them lapsed. The numbering was left with a gap rather than closed up, because a stage number is also its gate's name: G4: approved is a literal string that CI check 5, pnpm run check:g4, the issue template and every Story already approved are read for, and renumbering would either falsify it or leave G4 hanging off a Stage 3. The gate numbers already skip 3, 5 and 6 for the same reason. ADR-1005.
Two grills, and a round. The Feature grill at Stage 1 is a conversation and belongs to the conductor: one capability or several, the slug, the parent Epic, what it does not cover, which words enter CONTEXT.md. The Story grill inside Stage 4 is spec-author interrogating one Story’s edges, which are invisible until someone writes the delta — pulling them up to Stage 1 would settle four Stories’ worth of edge cases before any is built. But no subagent can ask you anything, so the Story grill writes instead: a question it may not settle goes into design.md under ## Questions for you, numbered, each with a recommended answer and what changes in the delta if you say otherwise. The folder is written anyway on those answers, so the round reaches you beside the diff it would change. The conductor relays it in the ordinary gate form. A stop, not a gate — no marker, no check, and only when there is a real question. ADR-1006.

One scenario at a time

A settled spec is a complete set of behaviours imagined before any code — which is exactly what the tdd skill calls horizontal slicing and names an anti-pattern. The resolution is consumption order: the spec is written up front, the tests are not.

One Story, one working tree, one PR

The archive is the last commit on the same branch, not a follow-up PR. That is what lets a single PR carry the spec, the code and the merge into the source of truth. The PR itself opens as a draft at Stage 4 and stays open to the merge: G4 reads it holding one commit, G7 reads it holding the whole Story, and it is rebased onto main before each.

What CI actually checks

Eight numbered checks on every PR, in one Linux job. Checks 2–6 are bespoke scripts in scripts/ — the most likely part of this system to rot. Four of the eight ask whether the Story is finished, and a draft PR asserts it is not, so they wait until it comes out of draft.

01Validate everythingopenspec validate --all --strict --no-interactive
02Spec-diff containmentEvery file changed under openspec/specs/ belongs to a capability the archived delta names. On a chore/ branch the set must be empty. This is the check that makes the source of truth safe.
03Single-change ruleA story/ PR adds exactly one directory under changes/archive/ and leaves no active folder behind.staged — reports locallyskipped on drafts
04Scenario coverageEvery #### Scenario: in the delta has an acceptance test whose title matches it verbatim, in Vitest or Swift Testing.staged — reports locallyskipped on drafts
05G4 approval recordedThe Story issue carries a comment beginning G4: approved <digest>, and the digest still matches the change folder. This is what turns “no implementation before G4” from a convention into a red build, and “approved” into “approved this”.skipped on drafts
06Commit hygieneNo commit on the branch carries an attribution trailer or names a tool. The history is a professional record.
07Verifypnpm run verify — lint, typecheck, test.
08Archive completeopenspec validate --archived — every tasks.md checkbox in the newly archived change is ticked.skipped on drafts

A second job exists for the product itself. swift runs on macOS, discovers every Package.swift in the tree rather than assuming a layout, and says out loud when it finds none — a green run that tested nothing would be worse than a red one. No Swift exists yet: ADR 1001 is the decision, not the first Story. The job is there so that the Story writing the first test does not also have to touch CI plumbing.

Why 3 and 4 are staged. Run locally on a Story still in flight they report rather than fail — the single-change rule reads “still active” until Stage 8, and coverage reports 2/4 covered — next: "<title>". Failing locally would demand every acceptance test at once, which is precisely the bulk transcription hard rule 3 forbids. In CI they bind, because a PR asserts the Story is finished.

Why 3, 4, 5 and 8 skip drafts. The PR opens at Stage 4, before a line of src/ exists, so that both human gates are read as a diff. On that day those four fail by construction: nothing is archived, no scenario is covered, and G4 has not been given yet. Skipping them is what makes an early PR usable instead of a permanent red X you learn to ignore — and 1, 2, 6 and 7 still run from the first push, so a draft proves the branch validates, stays inside its capabilities, keeps its history clean and passes lint, typecheck and tests. gh pr ready at Stage 8 restores the full list; the workflow subscribes to ready_for_review so it actually runs then.

The marker is the exact line G4: approved, not the bare word, because “approved” occurs constantly in ordinary prose — an agent writing “waiting on the approved comment” would otherwise forge the gate for any grep-based reader. It carries a digest of the approved change folder, so the gate records what was agreed and not merely that someone was asked. And one failure mode sits under all of this: project settings load from the session's startup folder, so a session started one directory above the repo gets no deny rules, no agents and no skills, and says nothing about it.

When not to run any of this

chore/<slug>

The escape hatch

No behaviour change, no Story, no Feature, and it may not touch openspec/specs/ at all — check 2 requires an empty set. Tooling, dependency bumps, docs, CI. Without this lane a one-line bump would need an Epic and you would abandon the process within a month. If you reach for it to add behaviour, that is the process telling you to write a Story.

< 2 hours

The proportionality rule

The gates cost roughly 45–90 minutes of your own time per Story, and that estimate held on the first run. A Story smaller than about two hours of work must not go through the full pipeline — batch it, or route it through chore/. One exception: a Story whose purpose is to exercise the pipeline itself, which must say so in its intent. Absent that sentence, a cold agent should push back rather than proceed.

if it hurts

Cut in this order

Drop the Epic level · fold Stage 7 into Stage 8 · drop CI check 3. That order is the one the retrospective rewrote against evidence: review was promoted out of the firing line at eight findings on forty-eight lines, the Epic carried nothing a Feature did not, and check 4 earns its keep by pacing the red-green loop rather than by ever failing. The cut that used to head the list — fold Stage 3 into Stage 4 — was taken on 30 August 2026, after it turned out to have already happened in practice. Never cut G4 or CI check 2 — those two are the process; everything else is scaffolding around them.

The real cost the estimate missed is not the gates. It is the machinery defects the gates surface — work created by a Story rather than contained in it. That decays as the system settles, but it was not zero on Story one and will not be zero on Story two.
